## 為什麼現在做

`TODO.md` 原本把「帳號 + 雲端同步」列在**不建議做**，理由是
「一個人用的話，匯出／匯入解決 90% 的需求」。那個前提已經不成立了：

- 現在有真的網域 + Let's Encrypt 憑證，手機上也要裝成 App
- 匯出／匯入是**覆蓋不是合併**。天天在手機與桌機之間手動搬，
  遲早會有一次拿舊的蓋掉新的，而且**不會有任何錯誤訊息**

更重要的是：**帳號與 `TODO.md` 3-c 的「公開部署門禁」是同一件事**。
現在後端**零認證** —— `/api/pronunciation-feedback` 沒有任何把關、收 8 MB 上傳、
直接燒 Azure 與講評的配額。任何連得到那個網址的人都能一直送。
做帳號順便把這個補起來，不必分兩次做。

> 一個對現況的更正：`TODO.md` 說 `/api/settings` 公開前必須移除。
> 實際上它已經安全了 —— `assertLocalRequest()` 只放行 127.0.0.1，
> 而在 Caddy 後面**所有**請求的來源都是代理的容器 IP，包含攻擊者的。
> 那條寫得比實際嚴重，實作時順手改掉。

## 目標與非目標

**目標**

1. 手機與桌機練習的進度自動合而為一，不必手動搬檔案
2. 所有 `/api` 端點要登入才能用（＝門禁）
3. 任何一邊壞掉（伺服器掛了、離線、帳號關掉）都還能繼續練

**非目標**（刻意不做，寫下來免得之後有人「順手加」）

- **不做密碼重設與 email 驗證。** 自己架的、使用者是自己，忘記密碼就去改
  `users.json`。加 email 等於多一組要顧的憑證與一條寄信的失敗路徑。
- **不做即時同步（WebSocket / SSE）。** 一個人不會同時在兩台裝置上練同一句。
  換頁與切到背景時同步就夠了。
- **伺服器不是唯一真相。** localStorage 仍然是本地的主資料，伺服器是可合併的副本。
  改成伺服器說了算的話，離線就不能練 —— 而離線能練是 PWA 的重點之一。
- **不做多人共享／班級功能。**

## 前提：先修一個會讓資料消失的問題

`docker-compose.yml` 的 `app` 服務**沒有掛任何 volume**。
容器裡寫的檔案在 `docker compose up --build` 重建映像時會全部消失 ——
使用者的全部學習進度。

所以第一步不是寫程式，是：

```yaml
  app:
    volumes:
      - userdata:/data
    environment:
      DATA_DIR: /data

volumes:
  userdata:
```

**Dockerfile 要先建好目錄並改擁有者**，因為映像檔裡是 `USER node`：

```dockerfile
RUN mkdir -p /data && chown node:node /data
USER node
```

漏掉 `chown` 的症狀是容器起得來、healthcheck 也過（`/api/health` 不碰資料），
只有第一次要寫進度時才 EACCES —— 而那時使用者已經練完一輪了。

> **目錄名不要用 `data/`。** 那個名字已經被手寫的面試練習句佔用
> （`data/interview.txt`，`import-sentences.mjs` 會讀）。
> 本機預設用 `./userdata`，容器裡用 `/data`，兩邊都由 `DATA_DIR` 決定。
> `.gitignore` 要加 `userdata/`。

## 伺服器端的檔案佈局

資料量小到不需要資料庫：`srs` 就算 10,040 個字全練過也才 0.57 MB，
`activity` 一年約 36 KB。一個使用者一個 JSON 檔就夠，**零新相依套件**。

```
$DATA_DIR/
  users.json              { "users": [ { id, username, passwordHash, createdAt } ] }
  sessions.json           { "<sha256(token)>": { userId, expiresAt } }
  u/<userId>.json         { rev, updatedAt, data: { srs, activity, vocabDays, history, settings } }
  u/<userId>.rev-<n>.json 最近 10 版的備份（見下）
```

`data` 裡的形狀**就是 `BACKUP_KEYS` 那五個鍵**，跟現有的匯出檔一模一樣。
`lib/backup.js` 的 `buildBackup()` / `readBackup()`（含全部的壞檔案檢查）
可以直接重用，不必為同步另外定義一套格式。

### 寫檔一定要是原子的

```js
await fs.writeFile(`${file}.tmp`, json);
await fs.rename(`${file}.tmp`, file);   // 同一個檔案系統上 rename 是原子的
```

直接 `writeFile` 到目標檔案的話，寫到一半斷電／容器被砍，
留下的是一個**被截斷的 JSON**，下次開啟就是「進度全沒了」。

### 保留最近 10 版

每次寫入前把舊的那份複製成 `u/<userId>.rev-<n>.json`，只留最近 10 版。
一份不到 1 MB，10 版也才幾 MB。

**理由：這整個功能最大的風險是合併寫錯、安靜地吃掉進度。**
留著舊版的話，發現不對時可以直接把檔案換回去；沒留的話，
使用者唯一的救援是自己之前有沒有手動匯出過。

## 帳號

### 威脅模型（先講清楚這個能擋什麼、不能擋什麼）

**擋得住**：路過的人燒掉你的 Azure／講評配額（這是現在真正的曝險）、
別人看到或改掉你的學習進度。

**擋不住也不打算擋**：有心人針對性的攻擊、伺服器本機被入侵、
你自己把密碼設成 `1234`。這是一個自架的、使用者是自己的 App，
不是要拿去給不特定多數人用的服務。

### 密碼

`node:crypto` 的 `scrypt`，不加任何套件：

- 每個使用者一組 16 bytes 隨機 salt
- `N = 2**15, r = 8, p = 1`，64 bytes 輸出（`maxmem` 要跟著調大，預設值會不夠而丟例外）
- 存成 `scrypt$32768$8$1$<salt base64>$<hash base64>` —— 參數存在字串裡，
  之後要調高成本時舊密碼還驗得動
- 比對用 `crypto.timingSafeEqual`，不要用 `===`

### Session

- token = `crypto.randomBytes(32)`，base64url
- **伺服器只存 `sha256(token)`**。這樣 `sessions.json` 外流不等於別人可以直接冒用
- cookie：`HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=30d`
  - `HttpOnly` —— XSS 也偷不到
  - `Secure` —— 只走 HTTPS（本機開發是 localhost，瀏覽器對 localhost 例外放行）
  - `SameSite=Lax` 而不是 `Strict`：Lax 已經擋掉跨站 POST（CSRF 的路徑），
    而 Strict 會讓「從別的 App 點連結進來」第一次看起來像沒登入，要重整一次才好
- 過期的 session 在讀取時順手清掉，不需要排程

### CSRF

`SameSite=Lax` 之外，**所有改變狀態的請求再檢查一次 `Origin` 標頭**
（不符就 403）。兩道是刻意的：SameSite 的行為在各家瀏覽器與各版本上有差異，
而 Origin 檢查是我們自己控制的、行為確定。

### 註冊要關起來

公開網域上開放註冊 = 任何人都能建帳號來燒你的配額。規則：

1. `users.json` 是空的時候，`POST /api/auth/register` 可以用一次 —— 建立擁有者
2. 之後**預設關閉**，回 403
3. 想再開的話在 `.env` 設 `INVITE_CODE`，註冊時要帶對才放行

### 登入失敗要退避

記憶體裡一張 `username|ip → { fails, until }` 表，連續失敗就指數退避
（1s → 2s → 4s …，上限 5 分鐘）。不需要套件，重啟就清掉也沒關係 ——
這是擋暴力猜密碼的鈍器，不是稽核紀錄。

## 端點

```
POST /api/auth/register   { username, password, inviteCode? }   → 201 + Set-Cookie
POST /api/auth/login      { username, password }                → 200 + Set-Cookie
POST /api/auth/logout                                           → 204 + 清 cookie
GET  /api/auth/me                                               → { username } | 401

GET  /api/sync                                → { rev, updatedAt, data }
PUT  /api/sync            { rev, data }       → { rev } | 409（rev 對不上）
POST /api/sync/merge      { deviceId, data }  → { rev, data }   ← 階段 B
```

### 哪些端點要登入

**全部 `/api/*` 都要**，只有兩個例外：

| 端點 | 為什麼不用登入 |
|---|---|
| `/api/health` | Docker 的 healthcheck 要用它，而 healthcheck 沒有 cookie |
| `/api/auth/*` | 還沒登入才會呼叫它 |

題庫（`/api/content/`、`/api/vocabulary/`）**也要登入**。它們不是機密，
但那是幾 MB 的靜態檔，不擋的話等於免費給人當 CDN。

> **service worker 要跟著改。** 快取的題庫在登出後應該清掉，
> 而且 `/api/auth/*` 絕對不能進快取（跟 `/api/settings` 同一條理由）。
> `sw.js` 的 `strategyFor()` 是唯一決定這件事的地方，改那裡就好。
> 401 的回應也不可以被快取起來 —— 不然登入之後還是一直看到「請先登入」。

### `rev` 是樂觀鎖

每個使用者一個單調遞增的整數。`PUT /api/sync` 帶著「我讀到的 rev」，
對不上就回 409 + 目前的整包資料，由前端決定怎麼辦：

- 階段 A：跳一個對話框問使用者要用哪一邊（並且講清楚另一邊會被蓋掉）
- 階段 B：直接合併，然後用新的 rev 再送一次

沒有這個的話，兩台裝置幾乎同時上傳，後到的會**無聲**蓋掉先到的。

## 合併規則（這是整個功能的核心）

每一個鍵的合併方式不一樣，而且**每一條都要是冪等的**
（同一份資料合併兩次的結果，要跟合併一次一樣），否則重試就會讓數字膨脹。

合併函式一律寫成 `lib/merge.js` 裡的**純函式**，不碰 localStorage、不碰網路 ——
這樣 `test/merge.test.js` 才測得到，而這是最不能出錯的一段。

### `history` —— 取聯集

每筆有 `at`（ISO 時間）與 `sentenceId`，用 `at|sentenceId` 當識別，
兩邊聯集、依 `at` 由新到舊排序、截到 `HISTORY_LIMIT`。

冪等：聯集本來就冪等。

### `settings` —— 整包取新的

`updateSettings()` 要開始寫一個 `updatedAt`。合併時比 `updatedAt`，
**整包取比較新的那一邊**。

不做逐欄位合併：那會產生一個「一半舊一半新」的組合，
而那個組合是使用者從來沒有選過的狀態。

### `srs` —— 每張卡取比較新的那一次

⚠️ **現在做不到，要先改資料形狀。** 現在一筆是 `{ box, due, seen, correct }`，
**沒有「最後一次作答的時間」**。`due` 不能拿來判斷新舊：
box 4 一週前答的卡，`due` 比 box 1 今天剛答的還晚。

所以 `recordAnswer()` 要多寫一個 `at: Date.now()`。合併規則：

1. 兩邊都有 `at` → 取 `at` 大的那一筆（整筆）
2. 只有一邊有 `at`（另一邊是加欄位之前的舊資料）→ 取有 `at` 的
3. 都沒有 `at` → 取 `seen` 大的那一筆；`seen` 也一樣 → 取 key 排序在前的那一邊
   （**一定要有一條決定性的規則**，不然每次同步結果都不一樣，兩台裝置會一直互相推翻）

> **已知的限制，要寫進 README：** 同一張卡在兩台裝置上、在兩次同步之間各答過一次時，
> `seen` / `correct` 會少算一次（取的是整筆比較新的那個，不是把次數加起來）。
> 要完全正確得做向量時鐘，對「一個人、偶爾換裝置」來說不划算。
> `box` 與 `due` 是對的 —— 那才是決定下次何時複習的欄位。
>
> **`at` 現在就該加，不要等到做階段 B 才加。** 早加早有資料；
> 等到要合併時才加，在那之前練的每一張卡都沒有依據可以比。

### `activity` / `vocabDays` —— 計數表，最容易寫錯的一個

現在的形狀是「一天一個數字」：

```json
{ "listening": { "2026-09-05": 2 } }
```

**取 max 和相加都是錯的。** 手機練 3 個、桌機練 2 個，同一天的真相是 5：

- 取 max → 3（少算）
- 相加 → 5，但**重複同步一次就變 10**（不冪等）

正確的形狀是每台裝置各記各的（G-Counter）：

```json
{ "listening": { "2026-09-05": { "dev-a1b2": 3, "dev-c3d4": 2 } } }
```

- **寫入**：每台裝置只加自己那一格
- **讀取**：把那一天所有格子加起來 → 5
- **合併**：逐格取 max → 冪等，而且不會少算也不會膨脹

`deviceId` 在第一次載入時產生（`crypto.randomUUID()`），存在 localStorage，
**不放進備份檔** —— 還原到另一台裝置時要是同一個 id，兩台就會互相覆蓋對方的格子。

#### 舊資料怎麼搬

已經存著的是數字（`{"2026-09-05": 2}`）。**不可以搬進「本機裝置」那一格** ——
兩台裝置各自搬一次的話，同一段歷史會被算成兩台的份而加倍。

搬進一個**固定的保留格** `legacy`：

```json
{ "2026-09-05": { "legacy": 2, "dev-a1b2": 1 } }
```

`legacy` 格跟其他格一樣取 max。手機的 legacy 是 2、桌機是 3 的話，合併後是 3
（不是 5）—— 同步之前的歷史會取兩邊比較大的那個，略為少算。

這個取捨可以接受：**同步之前的每日數字只餵連續天數**（只看那一天有沒有練過），
而今天的數字每天重新算。少算的部分不影響任何看得到的東西。

## 前端怎麼接

### 掛鉤的位置

`lib/storage.js` 的 `write()` 是**所有**寫入的唯一出入口
（`read()` / `write()` 是模組私有的，每一個 export 都經過它）。
在那裡標記 dirty 就好，不必去改五個模式。

### 什麼時候同步

| 時機 | 動作 |
|---|---|
| App 載入 | 先 `GET /api/sync` 合併下來再開始練 |
| 切到背景（`visibilitychange` → hidden） | 推上去 |
| 有 dirty 的寫入之後，debounce 10 秒 | 推上去 |

**不要每次寫入就同步** —— 練一輪單字卡會寫幾十次。

### 失敗了怎麼辦

**什麼都不做，繼續練。** 保持 dirty，下一個時機再試。
離線、伺服器掛了、session 過期，全部都是這個處理方式。

唯一要讓使用者看到的是 session 過期（401）：那要跳登入，
因為使用者不重新登入的話**永遠**同步不上去，而練習進度會一直只留在本機。
其他的失敗安靜重試就好，不要用橫幅打斷練習。

### 登入畫面

一個獨立的畫面（不是模式），在 `app.js` 啟動時先問 `GET /api/auth/me`：
401 就顯示登入，其他就照常進 App。

## 階段切分

### 階段 A：帳號 + 門禁 + 伺服器存檔

可以單獨上線，本身就是安全性的修補。

- Docker volume + `chown`（**先做這個**，不然資料會消失）
- `users.json` / `sessions.json` / 密碼雜湊 / cookie / Origin 檢查 / 登入退避
- 註冊規則（第一個帳號 → 之後要邀請碼）
- 全部 `/api` 要登入（除了 `/api/health` 與 `/api/auth/*`）
- `GET` / `PUT /api/sync`（整包上下傳 + `rev` 樂觀鎖 + 保留 10 版）
- 前端：登入畫面、401 處理、設定頁的「同步」區塊（手動上傳／下載）
- `sw.js` 的快取規則跟著改
- **順手把 `srs` 加上 `at`、`settings` 加上 `updatedAt`**（為階段 B 鋪路，早加早有資料）

這一階段的「同步」還是手動按的，但變成一鍵、而且隨時都在
（不必找檔案、不必在裝置之間傳）。

**驗收**：沒登入時每一個 `/api` 端點都回 401；登入後在 A 裝置練、
在 B 裝置按「下載」拿得到；重建容器（`docker compose up --build`）之後資料還在。

### 階段 B：自動合併

- `deviceId`
- `activity` / `vocabDays` 改成 G-Counter（含 `legacy` 搬家）
- `lib/merge.js` 的四條合併規則
- `POST /api/sync/merge`
- 前端改成自動（載入時拉、切背景推、debounce 推）

**驗收**：兩個瀏覽器設定檔各練一輪之後，兩邊的每日數字都等於**兩邊的總和**；
把同一次合併重跑三次，數字不變。

## 測試計畫

`lib/merge.js` 是純函式，所以最重要的那一段測得到：

| 測什麼 | 為什麼 |
|---|---|
| 每一條合併規則各自的行為 | 四種資料四種規則 |
| **冪等**：`merge(merge(a,b), b) === merge(a,b)` | 重試不能讓數字膨脹。這是最容易寫錯的性質 |
| **交換律**：`merge(a,b) === merge(b,a)` | 不成立的話，同步順序會影響結果 |
| 計數表：兩台裝置各練 N、M → 合併後正好 N+M | 直接釘住「不少算也不膨脹」 |
| `srs` 全部欄位都沒有 `at` 時仍然有決定性的結果 | 不決定的話兩台會一直互相推翻 |
| 隨機產生兩台裝置的操作序列，比對合併結果 | 上面幾條是舉例，這條是掃邊界 |
| 密碼雜湊：對的過、錯的不過、雜湊字串換成別的成本參數仍驗得動 | |
| session：過期的不放行、只存雜湊（明文 token 不在檔案裡） | |

UI 測試（`test/ui.mjs`）：沒登入會被擋、登入之後進得去、
登出之後題庫的快取清掉了。

## 會踩的雷（實作時回來看這一段）

- **Docker 沒有 volume ＝ 進度全沒。** 而且症狀是「重新部署之後從頭開始」，
  不會有任何錯誤訊息。第一件事就做這個。
- **`USER node` + 沒 `chown` ＝ 容器起得來、healthcheck 也過**，
  只有第一次寫進度時才 EACCES。
- **目錄名不要用 `data/`**（被手寫面試句佔用了）。
- **計數表不可以相加。** 相加不冪等，重試一次就翻倍。
- **舊的計數不可以搬進本機裝置的格子**，要搬進固定的 `legacy` 格，
  否則兩台各搬一次會加倍。
- **`deviceId` 不可以進備份檔**（`BACKUP_KEYS`）。還原到另一台會變成同一個 id，
  兩台從此互相覆蓋對方的格子。
- **`BACKUP_KEYS` 是白名單。** 加任何新的 localStorage 資料時第一件事是問
  「這個要不要進備份／同步」。漏加的症狀是「換一台裝置就少一種進度」，
  而且沒有錯誤訊息。
- **`srs` 沒有 `at` 就沒辦法正確合併**，而且加了之後才練的卡才有資料 ——
  所以在階段 A 就加。
- **401 不可以被 service worker 快取起來**，不然登入之後還是一直看到「請先登入」。
- **合併寫錯是靜悄悄的**。保留最近 10 版，發現不對時才有得救。
- **同步失敗不可以打斷練習。** 只有 401 要跳出來（不重新登入就永遠同步不上去），
  其餘安靜重試。
